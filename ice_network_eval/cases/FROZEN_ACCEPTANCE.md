# Frozen selection and acceptance rules for the baseline, interpolation-evaluation and challenge sets

Written and committed **before** any case of `baselines`, `param_eval` or `challenge` is executed, using development-set (`param_dev`, 32 points, 112 runs, 0 execution failures) results and the frozen S1-S5/closure/convergence results only. No later evaluation result may change these rules. If an evaluation reveals a defect that needs a code or rule correction, this evaluation version stays as published and a new, independent assessment is required (new cases drawn with new seeds).

## 1. Selected reduced configuration
**Primary: r17 = 17 stations per route, geometry step 450 s, 16 hydraulic substeps, ODE rtol 1e-7 / atol 1e-9, smooth-activation floor 1 mm.** Reason (development data only): r17 and r9 produce the same class counts (29 ok / 2 unexplained / 1 outside regime of 32 points each) and the same route accuracy on clear cases (28 of 28), while r17 has the lower median hydrograph error (0.0246 against 0.0331 of the inflow) at lower or equal cost; r33 was not run in the development set and is therefore not eligible as the primary configuration (it is reported where it exists in the frozen set). r9/dt900 is a secondary configuration reported for every case. The sets run exactly r9 and r17 and the 200-cell reference (every 4th point additionally 100 and 400 cells); no other settings.

## 2. Two separate questions per case
**A. Execution success.** A run is *successfully executed* if it completes without error, stall, timeout (900 s reduced / 1200 s reference), evaluation cap or process loss, and writes an immutable record. Execution success says nothing about accuracy.
**B. Acceptable predictive performance** (only for cases where both the reduced run and the reference completed): class `ok` of `cases/CHALLENGE_PROTOCOL.md`: hydrograph RMSE / mean inflow <= 0.10 against the reference (400 cells where run, otherwise 200) **and** the dominant outlet (larger delivered volume over the run) agrees whenever the reference's route margin |V1 - V2| / (V1 + V2) exceeds 0.10. Cases with margin <= 0.10 are `near_tie` and are reported separately (their route is not scored). The 0.10 thresholds were declared before the development analysis and are not tuned.
**Reported, not gating:** switching existence (R2 overtakes R1) and time, activation time, delivered volume per route, sill lowering per route, runtime, memory, conservation residuals, applicability flags.
**Classification of non-ok cases** is exactly the declared one: `failure_numerical` (execution failure/stall inside the envelope), `failure_outside_regime` (outside the declared envelope or the shared-assumption checks), `failure_unexplained` (inside both, completed, but not ok). **D003 and D012 stay `failure_unexplained`**: the only documented diagnostics for them (pulsed inflow; r_qs maxima of 790-960 at activation transients while the 90th-percentile flag passes; Froude >= 1 at 14-38 snapshots without flag violation) do not meet the declared outside-regime criteria, and no diagnostic supports another class. D009 stays `failure_outside_regime` (subcritical flag violated).

## 3. Applicability rules (unchanged from `CHALLENGE_PROTOCOL.md`, with its addendum)
quasi_steady: p90 of r_qs <= 1.0; subcritical: fraction of active snapshots with any station Froude >= 1 is <= 0.05; storage_neglected: p90 of channel/node volume <= 0.05; shared: channel not overtopping 1 m banks (maximum stage minus lowest sill < 1.0 m) and median per-snapshot maximum Reynolds number >= 2000. "Within both models" = all five hold.

## 4. Interpolation versus extrapolation
`param_eval` (64 points, Sobol seed 22, inside the development ranges `PARAM_RANGES`) = interpolation. `challenge` (32 points, Sobol seed 33, outside on every axis, `CHALLENGE_RANGES`) = extrapolation. Aggregates are computed separately for each set, and within each set separately for cases within / outside both models' assumptions. They are never pooled.

## 5. Matched-accuracy cost comparison (serial timing set)
Accuracy of a configuration = hydrograph RMSE/I against the 400-cell reference (frozen scenarios S1-S5). Cost = median of three serial repeats of the solver time (warm-up, sampling and serialisation excluded) on an idle single-worker machine. The reference's accuracy-cost curve is the log-log line through the 100- and 200-cell points (errors against the 400-cell reference); a reduced configuration is **matched** when its error lies between the 200- and 100-cell reference errors, and its speed-up is t_ref(err) / t_red. Outside that interval no speed-up is claimed. The reference errors carry the estimated error of the 400-cell target (`records/reference_uncertainty.json`).

## 6. Baseline comparison (existing-method surrogate)
Same lake, geometry, forcing, hydraulics and solver as the thermal network, with the incision law replaced by: T0 no melting (fixed terrain), T2 all channel dissipation melts the bed/walls (SaDS-type dissipation-only closure, Hill & Dow style; this is an approximation inside our hydraulics, **not** SaDS or SHED, whose code was not run), T3 = T2 with fixed-aspect geometry. Targets: the thermal reference (400 cells) for all, plus the no-melting reference (200 cells) for T0. Differences are *flagged* when: dominant outlet differs from the thermal reference; switching exists in one and not the other, or t_dom2 differs by more than the larger of 15 % and the thermal r17 error; relative sill-lowering difference exceeds 25 %. Flagged differences measure what the baseline misses under the shared hydraulics and thermal closure assumptions of the reference; they are not validation of either physics.
